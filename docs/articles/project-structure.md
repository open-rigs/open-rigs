# Experimental Repository Structure

When you run the copier template you are asked for three inputs:

| Input | Example | Description |
|---|---|---|
| `project_name` | `my-experiment` | Kebab-case name for this experiment |
| `author_name` | `Jane Doe` | Your name |
| `prefix` | `open-rigs` | Lab or organisation prefix (kebab-case) |

From these inputs the template auto-generates a set of internal names used throughout the project:

| Variable | Example | Used for |
|---|---|---|
| `python_folder_name` | `open_rigs_my_experiment` | Python module directory and import name |
| `python_package_name` | `open-rigs-my-experiment` | `pyproject.toml` package name |
| `dotnet_name` | `MyExperiment` | .NET class name fragment |
| `dotnet_full_name` | `OpenRigs.MyExperiment` | .NET namespace |
| `python_class_prefix` | `OpenRigsMyExperiment` | Prefix for generated Python/C# schema classes |

The resulting project looks like this (using `my-experiment` as an example):

```
my-experiment/
├── .bonsai/                        # Bonsai environment
│   ├── Bonsai.config               # Package references
│   ├── NuGet.config                # NuGet feed configuration
│   └── Setup.cmd / Setup.ps1       # Downloads Bonsai and installs the packages in Bonsai.config
├── .config/
│   └── dotnet-tools.json           # Pinned dotnet tool versions (e.g. Bonsai.Sgen)
├── config/
│   ├── rig-template.yml            # Generated by experiment/generate_rig.py; deploy.ps1 copies it to the machine's folder
│   ├── rigs/                       # Default ConfigRoot: one folder per machine, created by deploy.ps1, ignored by git
│   └── task.yml                    # Task parameters for one protocol, committed
├── experiment/                     # Generation scripts
│   ├── generate_rig.py             # Writes config/rig-template.yml from the rig model (run by regenerate)
│   ├── generate_session.py         # Writes an example session record to local/
│   └── generate_task.py            # Starts a new protocol's task file from the model defaults
├── scripts/
│   ├── deploy.cmd                  # Deploy script (Windows CMD)
│   └── deploy.ps1                  # Deploy script (PowerShell)
└── src/
    ├── open_rigs_my_experiment/     # Python module (your schema definitions)
    │   ├── __init__.py             # Package version helpers (__version__, __semver__)
    │   ├── regenerate.py           # The regenerate command: schema, C# classes, rig template
    │   ├── rig.py                  # Rig schema definition
    │   └── task.py                 # Task schema definition
    ├── Extensions.csproj           # .NET project for generated C# extensions
    └── main.bonsai                 # Main Bonsai workflow: loads rig.yml and task.yml, opens the session folder
```

### Key directories

**.bonsai/**
The self-contained Bonsai environment for this project. Running `Setup.cmd` downloads the Bonsai bootstrapper and installs every package listed in `Bonsai.config` into this directory. The experiment is then isolated from other Bonsai installations on the machine.

**src/open_rigs_my_experiment/**
The Python module where you define your experiment schemas. This is the main file you will edit when specifying experiment parameters. The module name is derived automatically from your `prefix` and `project_name` inputs.

**src/Extensions.csproj**
A .NET project that Bonsai uses to compile the generated C# schema classes (produced by `regenerate`). You generally do not need to edit this file directly.

**src/main.bonsai**
The starting workflow. It already does what every rig does first, with nothing typed in by hand:

1. `ResolveRigConfigDirectory` finds this machine's folder under `ConfigRoot`, a root property, and publishes it as `RigConfigDirectory`. `ReadRigConfig` reads `rig.yml` from it and the generated `DeserializeFromYaml` turns it into your rig type, published as `RigConfig`. A new project starts with `ConfigRoot` set to its own `config\rigs` folder, which `deploy.ps1` fills for this machine from `rig-template.yml`, and that folder is ignored by git. Once several rigs or repositories share configuration, change `ConfigRoot` to a common root such as `C:\RigConfigs` or a network share, on the workflow and in `deploy.ps1`.
2. `ReadAllText` reads the task file named by the `TaskFile` root property (`..\config\task.yml` by default) and the generated `DeserializeFromYaml` publishes it as `TaskConfig`. One committed task file per protocol; switch with the property.
3. `LogController` opens a session folder under the rig's `rootPath` (`SubjectId` and `SessionId` are root properties) and `LogSchemas` snapshots both configurations into it as `RigSchema` and `TaskSchema`.

Add your devices and task logic after these nodes. Each device include subscribes to `RigConfig` itself, with its own property mapping; task logic subscribes to `TaskConfig`. See [Rig Configuration](../bonsai-operators/OpenRigs.Core/rig-config.md) and the [A Rig on the Platform](a-rig-on-the-platform.md) tutorial. The workflow needs `regenerate` run once (the generated types) and `deploy.ps1` run on the machine (its `rig.yml`).

**config/**
`rig-template.yml` is generated by `experiment/generate_rig.py` and is the example rig file that ships with the project. `deploy.ps1` copies it to `<ConfigRoot>\<MACHINE-NAME>\rig.yml`, by default under `config\rigs\`, which git ignores: per-rig values are never committed. `task.yml` is the parameters of one protocol and is committed.

**experiment/**
The generation scripts. `generate_rig.py` instantiates the rig model with placeholder values and writes `config/rig-template.yml`; `regenerate` runs it after the schema and the C# classes, which keeps the template in step with the model. `generate_task.py` writes a task file with the model's defaults to a path you give it, as the start of a new protocol. It never overwrites an existing file, because task files are edited by hand. `generate_session.py` writes an example session record to `local/`, which git ignores.

**scripts/**
Helper scripts for deploying the project to a rig machine. See the [Build and Deploy](../tutorials/building-deploying.md) section for details.

### The schema compile step

Before opening Bonsai you need to run `regenerate` at least once. `deploy.ps1` does it for you; afterwards run it yourself:

```
uv run regenerate
```

It runs three steps in order and stops at the first failure:

1. Combines the `rig.py` and `task.py` schemas into a single JSON schema file in `src/DataSchemas/`
2. Calls `Bonsai.Sgen` to generate the C# classes Bonsai will use to read your configuration files in `src/Extensions/`
3. Runs `experiment/generate_rig.py` to rewrite `config/rig-template.yml`

You will need to re-run this step any time you change your Python schemas. Your task files under `config/` and the machine's `rig.yml` are not touched.
